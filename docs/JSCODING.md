Vanilla JS Web 开发专项约束

当项目使用 Vanilla JS（原生 JavaScript）开发 Web 前端时，除遵守上述通用原则外，还必须遵守以下约束。

1. 原生能力优先，禁止重复造框架

1. 优先使用浏览器原生 API、ECMAScript 标准能力、HTML 语义元素与 CSS 能力。模块组织优先使用 ES Modules（"import" / "export"）；网络请求优先使用 "fetch"；事件管理优先使用 "addEventListener"；数据展示优先使用安全的 DOM API。
2. 禁止为了展示架构设计而自行实现虚拟 DOM、响应式系统、通用状态管理器、依赖注入容器、模块加载器或复杂事件总线。只有存在明确、可验证的业务需求时，才考虑必要的抽象。
3. 简单页面优先采用明确的变量、函数和模块边界，不强制引入组件化体系。复杂交互只有在职责分离能实际降低维护成本时，才抽取独立模块、控制器或 Web Components。
4. 不得为了坚持 Vanilla JS 而拒绝成熟、必要的第三方工具；也不得因为缺少框架就直接手写复杂的通用基础设施。

2. DOM 生命周期与操作

1. 所有 DOM 操作都必须有明确的生命周期前提。确认入口脚本的执行时机、目标元素是否存在，以及动态创建和销毁元素时的处理方式。
2. 对必需的 DOM 元素，应及时发现并报告缺失或结构不符合预期的问题，不得通过大量可选链、空值回退或静默跳过来掩盖程序缺陷。对确实可选的元素才采用条件处理。
3. 修改现有页面时，必须检查相关事件监听器、输入值、焦点、选区及已有状态是否会受到影响。不要为了更新局部内容而无必要地重建整个 DOM 子树。
4. 动态内容渲染必须有明确的边界。用户输入、URL 参数、外部接口数据和其他不可信数据不得未经适当处理就进入 HTML、脚本、事件处理属性或危险 URL 上下文。
5. 普通文本优先使用 "textContent"；需要生成结构化 DOM 时优先使用 "createElement"、"append" 等原生 API。仅在确有 HTML 渲染需求时使用 HTML 解析入口，并根据数据可信度采用经过审核的 HTML 消毒方案。不得使用手写正则表达式代替通用 HTML 安全消毒器。

3. 事件监听与资源清理

1. 每个模块应明确初始化方式，避免同一功能重复注册监听器、重复启动定时器或重复执行初始化逻辑。
2. 对可能重复初始化、动态挂载或销毁的模块，应提供必要的资源清理方式。根据实际需要清理事件监听器、计时器、观察器、请求和其他长期持有的资源；优先复用 "AbortController" 等原生能力。
3. 动态列表可以根据事件密度和维护成本选择直接绑定或事件委托。事件委托必须正确处理 "event.target"、"closest()"、目标容器边界以及事件冒泡，不得假设事件目标始终是预期的直接子元素。
4. 不得无必要地阻止浏览器默认行为。表单提交、链接导航、键盘操作及指针事件必须遵循明确的业务意图。
5. 事件回调、异步操作和定时任务必须避免在页面状态已经失效或模块已经销毁后继续修改 DOM。

4. 异步操作与错误处理

1. 使用 "fetch" 时必须根据实际接口契约检查 HTTP 状态、响应格式和必要的业务字段。不得把 "fetch()" Promise 成功兑现直接等同于 HTTP 请求成功。
2. 对网络错误、HTTP 错误、解析失败、业务错误、超时与请求取消进行必要的区分。错误处理应保留足够的诊断信息，并向用户提供与操作场景相符的反馈。
3. 必须分析可能影响页面正确性的异步竞态。例如，旧搜索请求、重复表单提交或延迟返回的结果，不得覆盖更新的状态。根据需要使用 "AbortController"、请求序号、幂等控制或服务端协作机制。
4. 不得用空 "catch"、无条件返回默认值或吞掉异常的方式伪装成功。只有在存在明确的恢复策略时才捕获并处理异常。
5. 异步界面应在必要时处理加载中、成功、空结果、失败与取消等状态，避免重复提交、无限加载或不明确的失败反馈。

5. 状态、数据与浏览器存储

1. 简单业务优先使用明确的数据源和渲染函数，避免同一数据在多个变量、缓存和 DOM 节点中形成难以维护的重复状态。
2. 不得为了几个交互控件自行建立通用状态管理框架。只有出现真正复杂的共享状态、依赖关系或复用需求时，才评估相应工具。
3. "localStorage" 和 "sessionStorage" 只应在适当场景下用于客户端持久化。必须考虑数据解析失败、历史数据结构变化、存储不可用、容量限制和写入失败。
4. 不得假设客户端存储是可靠数据库，也不得把 JavaScript 可读取的存储区域视为安全的秘密存储。涉及重要数据、敏感凭证或关键业务状态时，应评估合适的服务端持久化和认证方案。
5. URL 参数、表单输入、存储数据、接口数据和 JavaScript 运行时对象应按照各自的数据类型处理。不要假设字符串就是数字、合法 JSON 就是合法业务对象，或客户端校验可以代替服务端验证。

6. 模块、路径与部署

1. 使用 ES Modules 时，应明确入口文件、导入导出关系及相对路径。避免使用未经必要性论证的全局变量、隐式加载顺序和循环依赖。
2. 本地验证必须采用符合目标运行环境的开发方式。使用浏览器原生模块时，优先通过本地 HTTP 服务器运行，而不是依赖 "file://" 环境。
3. 修改模块路径、资源地址、路由或构建配置时，必须考虑生产环境的部署前缀、大小写敏感文件系统、MIME 类型、CORS、CSP 和服务器路由回退等适用问题。
4. 如果使用 History API 实现单页路由，必须确认直接访问和刷新子路由时服务端行为正确；简单的多页面网站优先使用原生链接与独立 HTML 页面，不得无必要地自建完整 SPA 路由框架。

7. 浏览器兼容性、性能与无障碍

1. 实现前应明确目标浏览器及必要的最低版本。新 API 和语言特性必须与目标环境匹配，必要时采用特性检测和合理的降级方案。不得以 User-Agent 猜测代替能力检测，也不得为了未经要求的旧环境构建复杂兼容层。
2. 优先保证正确性与可读性，再根据真实的性能数据优化。避免不必要的 DOM 重建、频繁同步布局读取与写入、重复计算及主线程长任务。
3. "requestAnimationFrame"、防抖、节流、缓存、Web Worker 等优化措施应由实际需求驱动，不得为了形式上的性能优化无条件添加。
4. 优先使用语义正确的 HTML 元素，确保关键功能能通过键盘操作；根据交互需要处理焦点、表单标签、错误提示、弹窗行为和辅助技术可识别的状态。
5. 不得仅凭桌面浏览器上的鼠标操作就判断功能完成。应根据项目目标验证响应式布局、键盘交互、真实用户操作流程及必要的浏览器兼容性。

8. JavaScript 专项验证

1. 使用项目现有的构建、语法检查、Lint、测试和其他静态检查工具。不得为了执行检查而无必要地新增整套构建链、类型系统或框架。
2. 如果项目没有编译步骤，不得虚构或宣称已经完成编译。应执行适用于该项目的 JavaScript 语法检查、静态检查和浏览器运行验证；只有项目确实配置了相应编译或类型检查时，才报告这些检查的结果。
3. 严格模式与静态类型检查不是同一件事。ES Modules 默认采用 JavaScript 严格模式，但这并不等价于 TypeScript 类型检查、Lint 或完整的静态分析。不得混淆这些验证结果。
4. 全量冒烟测试必须覆盖本次修改涉及的用户操作、DOM 更新、异步请求、错误处理和关键调用链。对于本次新增且现有测试无法覆盖的关键行为，应补充适当测试。
5. 无法完成浏览器测试、生产构建或某项静态检查时，必须说明实际阻塞原因、已执行的检查及其结果，不得用语法检查通过替代运行验证。

执行原则： 这些约束是为防范真实的安全性、正确性和维护性问题，不是要求每个项目都实现完整的架构体系。始终根据当前需求选择最小但可靠的实现，优先使用项目已有能力与浏览器原生能力；只有明确的业务需求和实际风险才构成增加依赖、抽象层或基础设施的理由。
